# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Telegram bot for a small private group, written in Rust on top of [`telexide`](https://docs.rs/telexide). The headline feature is a **Polymarket-style prediction market**: browse live events and **buy YES shares of an outcome at the current price, then sell them back before settlement** (the "buy/sell shares" playbook). Two event kinds share one engine — **`sourced`** (Polymarket-backed, priced live from the Gamma API, house-banked) and **`amm`** (host-run via `/predict`, priced by an **LMSR** market maker, **LP-funded** through a funding stage that discovers the opening prices). Around that sit a coin ledger + transfers, fruit trading, and a daily check-in. State persists in a SQLite file in the working directory, chosen by the `BOT_DEV` flag via `database::db_filename(dev)`: `waterx-dev.db` for development (the default) and `waterx.db` for production (`BOT_DEV=false`) — so a dev bot never clobbers live balances. Configuration comes from environment variables (loaded from `.env` if present): `BOT_TOKEN`, `BOT_OWNER` (numeric Telegram user id), and optional `BOT_DEV` (default `true`; set `false` for production).

> **Coin-supply invariant (the rewrite's core rule).** The house mints coins (grows supply) **only** via (a) the daily check-in, (b) referral rewards, and (c) a player **winning a `sourced`/Polymarket market**. Host-run `amm` predictions never mint — they're a closed redistribution between the **LPs** (who seed the funding pool in a funding stage, bearing real bounded risk for the trading fee) and the traders, with the residual returned to LPs pro-rata. The engine's directed rounding is always pool-favorable, so an AMM escrow can't be drained below the winners' obligations. The trade engine lives in `src/database/event.rs` (+ the pure curves in `src/core/lmsr.rs` and `src/core/lmsr_fund.rs`), thoroughly conservation-tested.

The current command set is `start, assets, balance, bets, history, send, predict, events, rule, feedback, sell, buy, checkin, settings, timezone` — though only `start, balance, bets, history, send, predict, events, rule, feedback, settings` appear in the `/` menu (`assets`/`sell`/`buy`/`checkin`/`timezone` still work when typed but are hidden from `command_menu`). `/events` (formerly `/markets`) browses the live Polymarket feed; resolved bets **auto-settle** (a 5-min background Gamma sweep, with `/settle` as the manual fallback — there is no `/claim`). `/feedback` reaches the configured `BOT_OWNER` (`util::owner_id`) two ways: `/feedback <message>` (inline) DMs the owner immediately — message + sender (`name (@username, id …)`), best-effort — and confirms (`i18n::feedback_sent`); bare `/feedback` (no inline text) opens a **DM compose flow** like `/predict` — it DMs `i18n::feedback_ask`, registers a `Convo::Feedback` entry, and (in a group) replies `i18n::feedback_check_dm`; the user's next plain-text DM is forwarded by the `#[prepare_listener]` `feedback::on_message` (registered in `bot::run` next to `predict::on_message`), which then DMs `feedback_sent` and clears the draft. If the prompt DM bounces (the user never started the bot) → `i18n::feedback_dm_first`. The owner DM is sent via the shared `feedback::send_to_owner` helper used by both paths — sent as HTML (`tg::send_html`) so the sender's numeric id rides in a tap-to-copy `<code>` span (handy for a follow-up `/mint`/`/profile`); the name/username/body are HTML-escaped (`tg::escape`). `/balance` shows just the caller's coin balance and `/bets` just their open positions — **both work in DM *and* group** (a user opts into showing off by typing them, so unlike `/assets` neither hides anything in a group; `/bets` shows `i18n::no_open_bets` when there's nothing; in a **private** chat with open positions it also carries the `[💸 Sell]` button (`selling::SELL_PICK`), same as the `/assets` view — gated to private since the picker edits the message into the *tapper's* holdings). `/history` (`src/commands/history.rs`) is the caller's own **activity statement** — the last `HISTORY_LIMIT` (20) money/position actions, newest first, each line `<local time> — <emoji> <label>[ · <event title>]  <±coins>🪙` (`util::fmt_local_time` in the caller's `tz_offset`, `util::fmt_signed_coins`). In a **private** chat it's a **two-level** view: `/history` (and the `[🧾 History]` button) opens a **category menu** — **⛏ Mining** (check-in/referral/mint), **📈 Trading** (buy/sell/claim/LP + market void refunds), **↔️ Transfer** (send + envelope, incl. envelope refunds) — via `history::picker`; picking one (`hist:<tab>:<page>` → `history::page_view`) opens that category's **paginated** statement (`Database::user_history_by(tab, limit, offset)` + `user_history_count_by` for the `📄 x/y` count, `HISTORY_PAGE` = 10/page, `[◂ Prev][Next ▸]` + a `[⬅ Back]` → `menu:history` back to the menu). The overloaded `refund` tag is split by `event_id` — set → Trading, NULL → Transfer. In a **group** it's a static **flat** all-categories list (`history::flat_history_text`, newest 20), no menu, so a shared message can't swap to another member's view on a tap. Either way it's an opt-in show-off like `/balance`/`/bets` (**no counterparty names are rendered**, so it's group-safe), it's in the `/` menu, and has a private `[🧾 History]` home-page button (`menu:history`, edit-in-place → back to home, via the shared `history::picker` → `page_view`). It's backed by an append-only `history` table (`src/database/history.rs`) written **inside the same transaction as each money move** — the `pub(super) history::record(tx, user, kind, delta, event_id, counter)` helper is called just before `tx.commit()` in `event.rs` (`sourced_buy`/`sourced_sell`/`amm_buy`/`amm_sell` → `buy`/`sell`; `add_liquidity` → `lp_fund`; `settle_event` → `claim`/`refund` per winning/void user; `refund_liquidity`/`distribute_residual` → `lp_return`), `user.rs` (`transfer` → `send_out`+`send_in`; `reward_referral` + `try_checkin`'s upline cascade → `referral`; `try_checkin` → `checkin`), `referral.rs` (`reward_group_signup` → `referral`), and `buffer.rs` (the red-envelope path: `insert_buffer` → `send_out` when the envelope goes live, `claim_envelope` → `send_in` for the claimer, `refund_envelope` → `refund` back to the sender), so the statement **can't drift from the ledger** (a failed log rolls the money move back). The one exception is the owner `/mint`, which uses the generic `force_change` outside any engine tx and so logs **best-effort** via the standalone `Database::record_action`. Rows are **language-neutral** — a `database::HK_*` kind tag + signed micro-coin `delta` + optional `event_id`/`counter` — and rendered at read time (`Database::user_history` LEFT JOINs `events.title`, so a since-wiped event's rows still render label-only). The `HK_*` tags are re-exported from `database` (`pub(crate) use`) so the command's emoji/label map shares the exact literals the record sites write. Deliberately **not** logged: losing settlements (no coin move). Envelope creation's `send_out` rides in `insert_buffer`'s tx (not the earlier `balance_change` debit) because the Telegram post sits between debit and escrow-row insert, so there's no single tx spanning them. The `[Everything]` `/reset` and dev `/delete` clear the `history` table (the `[Markets]` reset leaves it — old rows just render label-only once their event is gone). `/assets` is the **combined** balance + positions view, **removed from the `/` menu** (still typeable) and kept for the `[💰 Check assets]` home button (`menu:balance`). Fruit display is **hidden until the fruit feature is designed** — the `fruit` column still exists and `/send`/`/sell`/`/buy` still move fruit, it's just not rendered. The shared renderers all live in `assets`: `balance_block` (name + balance line, or a db-error notice instead of a fake zero), `positions_block` (open share positions from the unified engine **+ open liquidity-provider stakes** `Database::user_liquidity` under `i18n::liquidity_title`, each with a 🌱/🟢 funding/live tag, `""` when none), and `assets_text(ctx, lang, user, show_balance)` which composes them. For the combined `/assets`, **`show_balance` is false in a group** (`util::is_group_chat`) so the balance stays private there — `/balance` is the explicit opt-in to expose it — and the `[💰 Check assets]` button is hidden in groups (its `menu:balance` path passes `true`, private-only). Open positions come from the **unified market engine** (`Database::user_positions` → `database::PositionView`): one line per open holding under `i18n::positions_title` — `• <event title>\n  <outcome> · 🪙<cost basis> → 🏆<shares>` (a winning YES share settles to 1 coin, so the share count *is* the potential payout). The same section covers **both** event kinds — Polymarket-backed `/events` matches and host-run `/predict` AMM markets are both `positions` rows.

The position lines are language-neutral (team/option names + numbers + symbols; the match side name is localized via the stored team names / `i18n::draw_label`). Plus owner-only admin commands `mint, pause, unpause, broadcast, reset, settle, redeploy, dashboard, backup, profile, delete` (gated on `BOT_OWNER` via `util::is_owner`; non-owners are silently ignored and these are deliberately kept out of the `/` command menu). `/delete` (owner **and** dev-mode only — `util::is_dev`, so it can never fire on a production bot) deletes a single user's profile — their `balance` row + any open `positions`, in one transaction (`Database::delete_user`) — so they count as **brand-new** again for referral binding (which gates on a `balance` row's existence), to re-test the referral flow without an `[Everything]` `/reset`. Target = the **replied-to user** or a numeric id (`/delete <id>`); there's no "self" default (an explicit target is required). It drops that user's open `positions` outright (no settle/refund — it's a referral-test helper, not a mid-trade cleanup). `/profile` inspects one user's state — balance, open share positions (`Database::user_positions`), referral links (`referrer`/`co_referrer` via `Database::get_referrers`), and referee count (`Database::count_referrals`) — for the **replied-to user**, a **numeric id argument** (`/profile <id>`), or the **owner themselves** when neither is given. It's sent via `tg::send_html` so the target user id rides in a tap-to-copy `<code>` span; every dynamic field is HTML-escaped (`tg::escape`). Plain English (an operator diagnostic, no i18n); it bails with a "no record" note when the id has never interacted (gated on `Database::user_exists`, so it never creates a phantom row). `/dashboard` replies with a plain-English bot-wide snapshot (an operator diagnostic, no i18n): user count + how many were referred, users who checked in today, group vs private chat counts, the **circulating coin supply** (sum of all `balance.balance`), live market-engine exposure — open Polymarket-sourced events (`/events`) + open host AMM events (`/predict`), open share positions, and coins committed (Σ position cost basis) — and the pause status. It's **one** `Database::dashboard()` call (`database::dashboard::Dashboard`, a single lock + a handful of `COUNT`/`SUM` aggregates over `balance`/`chats` and the engine `events`/`positions`). It carries **owner action buttons** (all `dash:*`, dispatched to `admin::handle_dashboard_action`, owner-gated even though the board is only posted to the owner), laid out as `[🔄 Refresh]` alone on the top row, then a 2×2 grid of the rest: `[⏸ Pause]`/`[▶️ Unpause]` (state-aware) · `[💾 Backup]` / `[⚙️ Settle]` · `[🚀 Redeploy]`. What each does: **Refresh** (`dash:refresh`) rebuilds in place; **Backup** (`dash:backup` → `snapshot`) toasts the file; **Settle** (`dash:settle`) runs the shared `settle::sweep`+`notify_settled`+`alert_failures`, same as `/settle`. The **disruptive** actions are **two-tap confirms** (via the shared `dashboard_confirm`, which swaps in `[⚠️ Yes, …]` / `[Cancel]`→`dash:refresh`): **Pause** (`dash:pause` → confirm → `dash:pause:go` → `set_paused(true)`; it blocks every non-owner action) and **Redeploy** (`dash:redeploy` → confirm → `dash:redeploy:go` → the shared `trigger_deploy`; restarts prod). **Unpause** (`dash:unpause` → `set_paused(false)`) fires directly — it's a safe recovery. Every action toasts its result and re-renders the snapshot in place; the text + buttons come from the shared `admin::dashboard_view`. The tappable set is the **no-argument** owner commands — `mint`/`broadcast`/`profile`/`delete` need input, so they stay command-only. No i18n (plain English, like the rest of `/dashboard`). `/redeploy` fire-and-forget triggers a **separate** systemd oneshot (`waterx-deploy.service` → `deploy/deploy.sh`: git checkout `dev` → pull → `cargo build --release` → `systemctl restart waterx-bot`) via `$REDEPLOY_CMD` (default `sudo systemctl start --no-block waterx-deploy.service`); it runs in its own unit so the restart can't kill the build, and is **inert until the operator installs the unit + sudoers** (see `DEPLOY.md`). On success `/redeploy` writes a marker file (`admin::REDEPLOY_MARKER` = `redeploy.notify`, holding the chat id); since the process that ran the command dies in the restart, the **freshly restarted** bot reads that marker in `bot::run` on startup, posts "✅ Redeploy complete — back online" to that chat, and deletes it. `/reset` (owner **and** dev-mode only — `util::is_dev`, so it can never fire on a production bot) posts a **multi-select picker** (`admin::handle_reset_cb`, callback prefix `rst:`): `[Markets]` / `[Everything]` each toggle a `✅`/`⬜` mark (the selection rides as a bitmask in the callback data — `rst:t:<flags>` re-renders, `rst:go:<flags>` executes), and `[🧹 Submit]` runs the picked parts — **Markets** refunds every committed coin and clears the trading engine (`Database::reset_events` — each holder's cost basis back + each AMM host's pool escrow `pool − Σ position costs`, then wipes `events`/`markets`/`positions`, in one conservation-safe transaction), and **Everything** does the **full** maintenance flow: (1) `reset_events` (so the snapshot captures those refunded coins), (2) **snapshot the whole DB** to the rolling `<db>.bak` (`Database::snapshot`) as the pre-wipe safety net, then (3) wipe every table (`Database::reset_all` — balance/buffer/meta/chats/group_adds/events/markets/positions). If the snapshot **can't be written, the wipe is aborted** (data is never lost). Everything **subsumes** the granular part and short-circuits it. Because it clears `balance` the same Telegram users become brand-new — referral binding gates on a row's *existence*, so they can be **re-referred** — and because it clears `chats` (the group adder), re-test the group-add referral by **kicking + re-adding the bot** (`on_my_chat_member` re-records `chats.added_by` on the Left/Kicked→Member transition), then members re-bind on their next interaction. **Backups are a rolling full-DB file snapshot**, not JSON. A background task spawned in `bot::run` snapshots the **whole SQLite DB** every `BACKUP_INTERVAL` (5 min) to a single `<db>.bak` in `DATA_DIR` (`Database::snapshot` → `snapshot_to`: a `VACUUM INTO` a temp file then an atomic rename — overwritten each time, **no timestamp** so it never grows, and it captures **every** table, not just balances). The first snapshot is one interval **after** boot, so a crash-looping deploy can't clobber the last good backup with a fresh-but-bad copy. `/backup` (owner-only) forces one on demand to the same `<db>.bak`; the `[Everything]` `/reset` writes one before wiping. **Restore is a file swap** (a live SQLite DB can't be hot-swapped under the open connection): stop the bot, copy `<db>.bak` over the live DB, restart (see `RAILWAY.md`). There's therefore **no `/load` command** — the old JSON path (`balances-*.json`, `Database::{export_accounts, import_accounts}`, `admin::{backup_balances, valid_backup_name}`) was removed. `/mint <amt>` credits whole coins (positive only — no debt) to the **replied-to user**, or to the **owner themselves** when sent without a reply; `/pause`/`/unpause` toggle a persisted kill-switch (`meta` table) that `util::paused_block` enforces at the top of every non-admin command and `callbacks::on_callback` enforces for button presses — the owner always passes through; `/broadcast <msg>` posts to every chat the bot has seen — private DMs **and** groups (`Database::all_chat_ids`), skipping failures. Chats are recorded into the `chats` table via `Database::touch_chat`, called from `util::paused_block` (top of every non-admin command) and `callbacks::on_callback`; group/channel ids are negative, private-chat ids positive (== user id). `/start` is the button-driven entry point: in a **private chat** a user picking a language is **always** then shown the **timezone picker**, and only after that the Wixy main menu (so the language flow doubles as "set timezone too"); a first-time user gets the language picker first (chaining language→timezone→menu); a returning user with a saved locale skips straight to the menu. In a **group** both pickers are skipped (it's a shared message) — the menu opens immediately in the sender's saved locale, or their Telegram-reported language (`Lang::from_user`) if unset. `/settings` (renamed from `/language`) **in a group opens privately** — the hub is a per-user edit-in-place surface, so it DMs the user (`i18n::settings_check_dm` reply in-group, or `settings_dm_first` if the DM bounces), like `/predict`/`/feedback`; in a private chat it posts in place. It opens a **hub** (`menu::settings_rows`) of three uniform click-in buttons — `[🌐 Language]` (`cfg:lang`), `[🕐 Timezone]` (`cfg:tz`), `[🎲 Format]` (`cfg:odds`) — each editing the message in place into its own picker that **`✅`-marks the current choice** (`menu::lang_picker_rows`/`tz_picker_rows`/`odds_picker_rows` each take the current value). The odds picker labels every format with a live 65¢ example (Decimal `1.54`, American `-185`, Percent `65%`, Price `65¢`); `setfmt:<code>` → `handle_set_fmt` persists `balance.odds_fmt` and **re-renders the hub in place** (so the odds pick returns to the hub, uniform with language/timezone); the odds picker's `[⬅ Back]` (`cfg:home` → `handle_cfg_home`) also returns to the hub if you don't pick. The language/timezone pickers opened **from the hub** emit **settings-variant** callbacks — `slang:<store_code>` / `stz:<minutes>` (via the `settings` flag on `menu::{lang_picker_rows, tz_picker_rows}`) — handled by `handle_settings_lang`/`handle_settings_tz`, which persist the choice and **re-render the hub in place** (the language one in the newly-chosen locale). So all three settings land back on the hub after a pick. The **onboarding** `setlang:`/`settz:` flow (used only by first-run `/start` and the standalone `/timezone`) is unchanged: it still chains language→timezone→menu. `/timezone` re-opens the timezone picker (**all** real-world UTC offsets, −12:00…+14:00 incl. the :30/:45 ones — `menu::TZ_OFFSETS`, 6/row — callback `settz:<minutes>`, persisted as **minutes east of UTC** in `balance.tz_offset`). The timezone is used to render **all absolute times** in the caller's local time in private chats — currently the `/markets` kickoff times (`markets::fmt_time`) and the brief's date header (`markets::fmt_date`); a group `/markets` is a shared message so it stays UTC. (The daily check-in stays on a fixed **00:00 UTC** boundary — never local-midnight — so a user can't farm it by hopping timezones; its "come back in 5h 23m" countdown is a duration, which is timezone-independent and so needs no localization.) `/timezone` works when typed but is hidden from the `/` menu (`/settings` is in it). The Wixy menu (`menu::menu_text(lang, tz)`) is a **time-aware greeting + intro/pitch** — `i18n::greeting(lang, part)` (a morning/afternoon/evening salutation, e.g. JA おはようございます/こんにちは/こんばんは, Taiwan 早安/午安/晚安) picked from the caller's local time via `util::day_part(tz_offset)` (bands 05:00–11:59 / 12:00–17:59 / else, `i18n::DayPart`), prepended to `i18n::intro(lang)` (the bot introduces itself as **Wixy** with the World Cup pitch; no per-user name); the balance is **not** shown here (the `[💰 Check assets]` button covers it). It has inline buttons (one per row, `menu::main_menu_rows(lang, checkin_available, is_group)`) firing the `setlang:` / `menu:` callbacks. **Private chats** show `[💰 Check assets]` (`menu:balance`, **edits the message in place** into the full `/assets` view incl. open positions via the shared `assets::assets_text`, + `[⬅ Back]` → `menu:home`), `[🧾 History]` (`menu:history`, **edits in place** into the caller's tabbed `/history` activity statement via the shared `history::picker`, then `page_view` per category + `[⬅ Back]` → `menu:home`), `[today's matches]` (`menu:markets`, also **edits in place** to the match brief + `[⬅ Back]` → `menu:home`), `[📜 How to earn coins]` (`menu:rule`, edits in place into the `i18n::rules_text` brief + `[⬅ Back]` → `menu:home`), `[🔗 Invite friends]`, and `[daily check-in]` on top when claimable (`Database::checkin_available`). **Group chats** (negative chat id, `util::is_group_chat`) get a single shared message, so only the **shared** buttons show — `[daily check-in]` (always shown, never dropped after a claim, so every member can claim — per-user gating still happens in `try_checkin`), `[today's matches]`, and `[🎲 Create prediction]` (`menu:predict` → `handle_menu_predict`, which opens the `/predict` builder exactly like the command via the shared `predict::open_draft`); the per-user `[Check assets]` / `[Invite friends]` and the `[How to earn coins]` buttons are **hidden** in groups (rule/invite/balance are private-only). In private chats the check-in button drops off once the caller has claimed. The home page deliberately carries **no** referral deep-link button (it'd be a private-info surface). Instead, `[🔗 Invite friends]` (`menu:invite`, private chats only) **edits the current message in place** into a **chooser** showing the caller's **referral count** (`i18n::invite_count` via `Database::count_referrals`) above three format buttons (`i18n::invite_how`) plus a `[⬅ Back]` (`menu:home` → re-renders the main menu via `handle_menu_home`). Menu navigation is **edit-in-place** (one message morphs, not a pile of new ones): the artefact is generated **only when the user picks one** (in `callbacks`):
The three invite artefacts are each posted as a **new message** (the chooser is left in place, so the user can pick more than one format) — only the chooser/menu navigation itself is edit-in-place:
- **`inv:link` — copyable link**: `handle_invite_link` sends a **new** message with the referral link in a tap-to-copy `<code>` span (`tg::send_html`, HTML `parse_mode`), no keyboard.
- **`inv:fwd` — forwardable message**: `handle_invite_fwd` sends a **new** message — a friendly one-liner (`i18n::invite_forward`) with the link in **plain text** (so it survives a forward — inline keyboards don't) **plus the `[🎮 Play now]` URL deep-link button** (`menu::referral_link`, needs `BotUsernameKey`), via `tg::send_with_buttons`.
- **`inv:qr` — QR code** (the one exception — Telegram can't edit a text message into a photo): `handle_invite_qr` sends a **single new photo** — a QR of the link (generated **locally** via `qrcode_generator::to_png_to_vec`, no third-party service), caption = the **bare link** (count is on the chooser, not here), and **no keyboard** (the link rides in the caption/QR image). The QR is identical every tap (the link is immutable), so Telegram's returned **`file_id`** is cached per user (`callbacks::qr_cache`, in-memory `OnceLock<parking_lot::Mutex<HashMap<i64,String>>>`) and re-sent via `tg::send_photo_id` with no regeneration/upload on later taps; only the first tap (or first after a restart) uploads via `tg::send_photo_bytes`, which returns the `file_id`. (A bot can't read arbitrary DM media, but it can re-send its own uploads by `file_id`.) `tg::send_photo_bytes` posts the multipart `sendPhoto` directly via `reqwest` (token from `util::bot_token`) rather than telexide's `send_photo` — **telexide's file-upload path is broken**: it serialises the `photo` field as `attach://qr.png` but names the multipart part `qr` (truncated at the first `.`), so Telegram never matches the attachment and the upload silently fails (this also lets us attach a `reply_markup`, which telexide's button struct can't — see `tg.rs`'s header). On forwarding, Telegram **strips the entire inline keyboard** (callback *and* `url` buttons) — which is exactly why the `[Play]` button lives on the forwardable text message, not here; a forwarded QR relies on the **caption link text** and the **QR image** (link baked in). The QR path is best-effort: on any failure it falls back to a plain `util::send_text` (link + count). **Referral system** (three surfaces, one binding/payout path — shared payout in `referral::pay_referral`, which credits **both** sides `referral::REFERRAL_REWARD` = 10 and DMs the referrer via `i18n::referral_bonus`):
1. **Deep link** — a user opening someone's link sends `/start <referrer_id>`; `start` records it once via `Database::set_referrer_if_unset` (referrer must already exist, must differ, and the referee must have **no referrer yet** — a brand-new row **or** an existing referrer-less one, the friendly late-bind). It returns `true` only on the `referrer` `0 → set` transition, so each referee pays out at most once (the transition is one-directional).
2. **Group add** — two things record an "adder". (a) When the **bot** is added to a group, the `callbacks::on_my_chat_member` listener (registered via a second `add_handler_func`; fires on `UpdateContent::MyChatMember` when status goes Left/Kicked → Member/Admin/Creator) records the bot-adder in `chats.added_by` (first adder wins, `Database::set_group_adder`). (b) When a member **A adds another member B** to a group that already has the bot (a `new_chat_members` service message — `MessageContent::NewChatMembers`, delivered even under privacy mode), the `callbacks::on_new_members` listener (a third `add_handler_func`, matches `UpdateContent::Message`) records `A` as `B`'s adder in the `group_adds(chat, member, adder)` table (`Database::record_group_add`, first-adder-wins; the **bot itself** and **self-joins** — `from == the new member`, e.g. joined via invite link — are skipped, so those fall back to the bot-adder). When a **referrer-less** user then has **any interaction** with the bot in that group — a **button tap** (`callbacks::on_callback`, before dispatch) **or a text command** (`util::paused_block`, top of every non-admin command) — the shared `referral::maybe_bind_group(ctx, chat_id, user)` binds them (a brand-new row **or** an existing one whose `referrer` is still empty — the friendly late-bind). **The referrer is whoever added _that member_ (`group_adds`, `Database::group_add_referrer`) if known, else the bot-adder (`chats.added_by`) as the fallback — and the group _owner_ (Telegram creator) is the 0.5 co-referrer**: the owner is resolved lazily (`referral::resolve_group_owner` → `tg::chat_creator` via `getChatAdministrators`, cached in `chats.owner`, distinct from the adder) and, **when different from the adder**, stored as the referee's `balance.co_referrer` (`Database::bind_group_referral`, after `force_change` on both so they have rows). The signup bonus is then **split 50/50** between adder and owner (`Database::reward_group_signup`; referee still gets the full `REFERRAL_REWARD`), each DM'd their share (`referral::pay_group_referral`); when adder == owner or the owner is unknown, the adder is the sole referrer (full reward). It short-circuits on a `Database::has_referrer` fast-path so already-referred members do a single read and bail (no per-interaction write); it's a no-op outside groups, for already-referred users (`bind_group_referral`'s atomic `0 → set` guard — insert a fresh row **or** fill an existing referrer-less one, once, so no double-pay), or when **no** adder is known (neither a `group_adds` record nor `chats.added_by`). Both call sites run **before** the command/handler creates the user's row, preserving the referrer-less check; binding before dispatch means it's in place for whatever follows (e.g. check-in's upline cascade). Plain group chatter is **not** a trigger — Telegram privacy mode only delivers commands, button callbacks, and service messages (like `new_chat_members`) to the bot.

A user is bindable on either path as long as they have **no referrer yet** — a brand-new account **or** an existing one that never got a referrer (the friendly late-bind). Once bound, a referrer is never overwritten, so each referee triggers the signup reward **at most once** (the `referrer` `0 → set` transition is one-directional — no farming). On top of the one-time signup reward, **every successful check-in pays a referral cascade up the chain** inside `Database::try_checkin`: the direct referrer +1 coin, the referrer-of-referrer +0.1, and one level above +0.01 (`CHECKIN_UPLINE`). When the referee has a **co-referrer** (a group-add bind where the owner ≠ adder), the **direct (level-1) reward is split 50/50** — adder +0.5, owner +0.5 — while the deeper 0.1 / 0.01 levels follow the **adder's** chain only (the owner is a level-1 co-credit, not a chain node).

**Money model:** balances are stored as integer **micro-coins** (6-decimal fixed-point — `database::COIN = 1_000_000` units = 1 coin), kept as `i64` (not `u64`: SQLite integers are signed, ledger deltas are signed, and the non-negative invariant is enforced by `balance_change`'s guard, not the type). Outcome **shares** use the same fixed-point unit — `event::SHARE = 1_000_000` micro-shares — and **`SHARE == COIN`**, so a winning share settles to exactly one coin. The LMSR/price math runs in `f64` then quantizes to these integers at the ledger boundary with **pool-favorable** directed rounding (buy shares floored, sell refunds floored), so rounding can never drain an AMM pool below its winner obligations. User-typed whole-coin amounts (send/sell/buy/mint/stake) are multiplied by `COIN` at the ledger boundary; balances are displayed with `util::fmt_coins`, which rounds to **at most 2 decimals** (half-up, trailing zeros trimmed — so "42", "0.5", "7.69") for display only; the ledger keeps full micro-coin precision. Balances are stored directly in micro-coins with **no startup rescale** — an earlier `×COIN` legacy migration was removed because it double-scaled balances whenever `/reset` wiped its `meta` guard flag. There is no debt path, so the old `debt_coins` message was removed and `/assets` always renders "has". **Atomicity invariant:** `balance_change` is a single conditional `UPDATE … WHERE balance + ?1 >= 0` (atomic, no read-then-write TOCTOU), and every multi-statement money/state mutation runs inside one rusqlite transaction — `Database::transfer` (direct `/send`), the **share-trade engine** (`sourced_buy`/`sourced_sell`, `amm_buy`/`amm_sell`, `create_amm_event`/`create_funding_event`/`add_liquidity`, and `settle_event`/`settle_all_resolved` — each atomically moves coins ↔ shares/pool with the atomic debit guard), `reward_referral` / `reward_group_signup` (referral legs — the latter splits the referrer share 50/50 with the group owner), `try_checkin` (reward + the upline cascade, incl. the level-1 co-referrer split), `fruit_transfer` (debit + credit), `claim_envelope` (delete-then-credit, exactly-once under concurrent taps), the startup `refund_and_prune_old_buffer` (refunds expired sell/buy escrow **and unclaimed-envelope escrow** — the sender was debited at creation and the amount lives in the row's `price` — then deletes, all in one tx; an envelope refund also logs a `refund` to `/history`), and the `buffer` escrow/fill/refund paths (`open_*_offer`, `consume_*`). So a mid-sequence failure can never leave money half-moved, and concurrent debits can't overdraw. Whole-coin amounts from callback data are converted with `util::to_micro` (caps at `MAX_COINS`, `checked_mul`) before any `× COIN`, so a crafted stake can't overflow `i64`. DB read failures **fail safe**: `assets`/`/settle`/`/broadcast` surface the error instead of masking it as a zero balance / empty list, and the pause kill-switch **fails closed** (an unreadable `is_paused` flag blocks non-owners — the owner is checked first, so they can still `/unpause`). **Odds display format** is a per-user preference (`types::OddsFormat` = Decimal/American/Percent/Price, default Decimal) set via the `/settings` hub and persisted in `balance.odds_fmt` (`Database::{get_odds_fmt, set_odds_fmt}`). The single formatter `util::format_odds(cents, fmt)` turns a YES price into a display string (Decimal `1.54`, American `-185`, Percent `65%`, Price `65¢`) and is used at every odds-rendering site: the `/markets` brief (`render_market`/`brief`, caller's format), the match card (`quote_text`/`option_rows`, the **creator's** format pinned in the `opt:<lang>:<fmt>:<key>:<idx>` button so a shared card never flips per tapper), the DM stake builder + `bet_placed`/`bet_announce` (the bettor's format). The DB schema is `balance(user, balance, fruit, last_checkin, lang, referrer, co_referrer, tz_offset, odds_fmt)` (`referrer`/`co_referrer` = the two group-add co-referrers, 0 = none; `tz_offset` = minutes east of UTC, **nullable** — NULL = not yet picked, `Database::{get_tz, set_tz}`; `odds_fmt` = empty → Decimal) + `buffer` + the **unified market** tables (owned by `database/event.rs`): `events(id, kind, source_ref, title, creator, lang, odds_fmt, tz_offset, ends_at, state, winning_market, b_param, fee_bps, pool, card_chat, card_msg, created_at, resolved_at, open_at)` (`kind` = `sourced`|`amm`; `source_ref` = the Gamma slug for sourced events; `state` = `funding`/`open`/`resolved`/`closed`/`void` — an `amm` funding-stage event starts at `funding`; `pool`/`b_param`/`fee_bps` = the AMM seed pool / LMSR liquidity / host trading-fee bps; `open_at` = when an amm funding stage closes → trading opens lazily; `winning_market` = the resolved outcome idx; `card_chat`/`card_msg` = the board message, so a bet can re-render it) + `markets(event_id, idx, name, q_shares, funded)` (one tradeable outcome per row; `q_shares` = net YES **micro-shares**, the AMM price input; `funded` = the per-outcome funding-stage allocation in micro-coins — the price-discovery tally) + `positions(event_id, market_idx, user, shares, cost)` (a user's YES micro-shares + micro-coin cost basis) + `liquidity(event_id, user, contributed)` (each LP's funding contribution in micro-coins; LP pool share = `contributed / Σ`, used to split the residual + fees pro-rata at resolution — the single-host `create_amm_event` seeds the host as its sole row, unifying the resolve/void/reset paths) + `history(id, user, at, kind, delta, event_id, counter)` (the append-only per-user action log behind `/history`, owned by `database/history.rs`; `kind` = an `HK_*` tag, `delta` = signed micro-coins, `event_id`/`counter` = optional related-market / transfer-counterparty ids; index `idx_history_user (user, id DESC)` for the newest-first read) + `meta` (key/value flags: the `paused` kill-switch) + `chats(chat, seen_at, added_by, owner)` (every chat the bot has seen, for `/broadcast`; `added_by` = who added the bot to that group, `owner` = the group's Telegram creator cached lazily — both feed the group-add co-referral) + `group_adds(chat, member, adder)` (who added a specific member to a group — from a `new_chat_members` service message; consulted at that member's first interaction to bind them to the person who added them, taking priority over `chats.added_by`; owned by `database/chats.rs`). The old `wagers` + `games`/`game_options`/`game_stakes` tables were **removed** (the share engine replaced both); `Database::new` best-effort `DROP TABLE IF EXISTS`es them on boot to clean any pre-rewrite data file. `balance.referrer` is the inviter's user id (0 = none); `Database::count_referrals` counts a user's referees. `/checkin` grants 10 coins once per UTC day — `last_checkin` stores the last claimed UTC day index (`unix_secs / 86400`), so the window resets exactly at 00:00 UTC (see `Database::try_checkin`). A vestigial `cloth` column was dropped (a startup migration `ALTER TABLE balance DROP COLUMN cloth` cleans up old data files).

## Architecture

### Framework version

`Cargo.toml` pins `telexide = "0.1.17"`. **There is no `0.31`** — an earlier commit pinned that and it doesn't resolve. If you see references to a newer telexide version anywhere, treat them as suspect and check `https://crates.io/crates/telexide` before bumping.

### One file per command

`src/commands/<name>.rs` holds exactly one `#[command]`-annotated async fn. `commands/mod.rs` re-exports each with `pub use <name>::*;` so the proc-macro-generated `<name>_COMMAND` static is also re-exported. `src/bot.rs` does `use crate::commands::*;` and lists every command identifier in `create_framework!` — adding a command means:

1. New file under `src/commands/`
2. `pub mod foo;` + `pub use foo::*;` in `commands/mod.rs`
3. Append `foo` to the `create_framework!` ident list in `bot.rs`

### Shared state via `TypeMapKey`

`bot.rs` defines the keys `DbKey`, `ConfigKey`, `BotIdKey`, `BotUsernameKey`, `QuotesKey` (the match-bet quote store), and `ConvosKey` (in-flight `/predict`/`/feedback` DM drafts). Handlers reach DB state through `db(&ctx) -> Arc<Database>` in `src/commands/util.rs`; the rest are read directly via `ctx.data.read().get::<…>()` at the few sites that need them.

These helpers also encapsulate the **Send-across-await gotcha**: `ctx.data.read()` returns a `parking_lot::RwLockReadGuard` that is **not `Send`**, so it cannot be held across `.await`. The helpers grab the value and let the guard drop on the same statement — always go through them rather than calling `ctx.data.read()` inline.

### Callback queries are routed separately

Telegram callback queries (inline-button presses) are *not* commands. They come through `src/commands/callbacks.rs::on_callback`, a `#[prepare_listener]` registered via `add_handler_func` in `bot.rs`. It matches `UpdateContent::CallbackQuery` and dispatches on the `cb.data` string prefix. **Share-trading** prefixes: the `/events` brief pagination `evpage:<m|s>:<page>` (`markets::PAGE` → `callbacks::handle_events_page`, edit-in-place re-render), the sourced match-bet **buy** flow `bet:`/`opt:`/`sz:`/`szp:` (`markets::BET` + `betting`), the **sell** flow `slpick`/`slb:`/`slgo:` (`selling`), the AMM `/predict` board `pm:buy:`/`pm:sz:`/`pm:go:` (buy) + the **funding stage** `pm:fund:`/`pm:fsz:`/`pm:fgo:` (LP liquidity) + `pm:resolve:`/`pm:win:`/`pm:void:`/`pm:back:` (host-resolve) (`predmarket`), the `/predict` builder's fee + funding-window pickers `pmfee:`/`pmfund:` (`predict::handle_predict_fee`/`handle_predict_funding`), and the shared owner-locked-board `bx:` (Dismiss). Plus `envelope:`, fruit `sell:`/`buy:`, the onboarding `settz:`/`setlang:` and the `/settings`-hub `stz:`/`slang:` (+ `setfmt:`, `cfg:lang`/`cfg:tz`/`cfg:odds`/`cfg:home`), `menu:checkin`/`menu:home`/`menu:balance`/`menu:bets`/`menu:history`/`menu:markets`/`menu:rule`/`menu:predict`/`menu:invite`, `inv:link`/`inv:fwd`/`inv:qr` (invite-format chooser outputs), and `rst:` (owner+dev `/reset` picker → `admin::handle_reset_cb`), the `/history` category pages `hist:<tab>:<page>` (→ `callbacks::handle_history_tab` → `history::page_view`, per-tapper, edit-in-place), and the owner `/dashboard` action buttons `dash:*` (`dash:refresh`/`dash:pause`/`dash:pause:go`/`dash:unpause`/`dash:backup`/`dash:settle`/`dash:redeploy`/`dash:redeploy:go` → `admin::handle_dashboard_action`). (The old pari-mutuel `gamble:`/`gsz:`/`gsc:`/`gsp:`/`pstl:` and owner button-settle `stl:` prefixes — and the `menu:settle`/`menu:repost` home buttons — have been **removed**; the share engine + the public `/settle` replaced them.) The `menu:*`/`setlang:` ones drive the `/start` menu (defined in `src/commands/menu.rs`): `setlang:<store_code>` saves the locale and edits the picker into the main menu in place; `menu:checkin` grants the daily reward as an alert and (in private chats) refreshes the menu to drop the now-spent button; `menu:balance` **edits the menu in place** into the caller's balance + open positions (the shared `assets::assets_text`) + `[⬅ Back]` → `menu:home`; `menu:bets` **edits in place** into the open-positions view (the `/bets` surface — positions only, no balance) + `[💸 Sell]` (when holding) + `[⬅ Back]` → `menu:home`; it's the **sell flow's back target** (`handle_sell_pick`/`handle_sell_place` return here, so selling from either `/assets` or `/bets` lands back on the positions list); `menu:history` **edits in place** into the caller's history **category menu** (the shared `history::picker`) + `[⬅ Back]` → `menu:home`; the `hist:<tab>:<page>` buttons (`callbacks::handle_history_tab` → `history::page_view`, per-tapper) open a category's paginated page, whose `[⬅ Back]` returns to `menu:history`; `menu:markets` **edits in place** into the match brief (via the shared `markets::brief`) + `[⬅ Back]` → `menu:home`; `menu:home` re-renders the main menu (`handle_menu_home`); `menu:rule` edits in place into the "how to earn coins" brief (private-only button); `menu:predict` (group-only button) opens the `/predict` builder for the presser via the shared `predict::open_draft` and toasts them to their DM (or "DM me first" if it bounces) — identical to running `/predict` in the group. `menu:invite` posts the invite-format chooser, and `inv:link`/`inv:fwd`/`inv:qr` generate the picked format on demand (copyable `<code>` link / forwardable text / cached-`file_id` QR photo — see the `/start` menu section). A second `#[prepare_listener]`, `callbacks::on_my_chat_member` (also registered via `add_handler_func`), watches `UpdateContent::MyChatMember` to record who added the bot to a group (`chats.added_by`) for the group-add referral path. A third, `callbacks::on_new_members`, watches `UpdateContent::Message` for `new_chat_members` service messages to record who added each **member** (`group_adds`) — the member-specific referrer that takes priority over the bot-adder.

Logging is error-only on stderr via `eprintln!` (DB/save failures, getUpdates/parse errors, setMyCommands failures, markets fetch failures), with **one** exception: a single startup line (`waterx-bot ready: @<user> (id <n>), <dev|production> mode`) printed by `bot::run` right before the poll loop. Keep new logging to error paths only (plus that one ready line).

**Owner alerts.** Failures the operator should *act on* — but wouldn't otherwise see — don't just log; they also DM the `BOT_OWNER` via `util::alert_owner(ctx, what)` (handler paths) / `util::alert_owner_token(token, owner, what)` (background tasks with no `Context` — the auto-settle + backup loops, which get the token/owner passed in from `bot::run`). Both funnel through `alert_owner_token`, which is the single home for the stderr log, the `⚠️` prefix, and a **5-min dedup throttle** (`ALERT_DEDUP_WINDOW` via `alert_recently_sent`, a process-wide `OnceLock<Mutex<HashMap<msg,Instant>>>`) so a persistent failure (a down DB, an outage firing on every interaction) can't flood the owner's DMs or trip Telegram's rate limit — the log is never throttled, only the DM. Wired into the money/state-integrity + not-owner-watching paths: the share-trade engine failures (`sourced_buy`/`get_or_create_sourced_event`/`amm_buy`/`add_liquidity`/`sell`, `betting`/`selling`/`predmarket`), settlement (`settle::sweep` enumerate error, per-event settle failures surfaced up via `database::SettleReport { payouts, failed }` from `settle_all_resolved`, the manual-settle handlers, and the AMM host-resolve/void settle), referral payouts (`pay_referral`/`pay_group_referral`), the red-envelope refund/escrow paths (`send`), envelope claim (`callbacks`), the `/predict` create + placeholder post, the match-bet feed fetches + stake-board post (`betting`), the `/assets`/`/bets`/`/history` DB reads, the fail-closed pause reads (`callbacks`/`paused_block`), the generic callback-handler error sink, the owner admin ops (`redeploy`/`delete`/`reset`/`broadcast`), `/mint`'s best-effort history log, and the **background backup** snapshot failure. Deliberately **eprintln-only** (no owner DM): the poll loop / startup (`getUpdates`, `getMe`, `setMyCommands`, redeploy-notify — Telegram is unusable or mid-init when these fire, so a DM can't send), the `feedback` owner-DM failure (circular — it's the owner DM that failed), the per-event settle log in `settle_all_resolved` (already surfaced to the owner via `SettleReport.failed`), `tg::post_edit`'s generic edit-message failures (very high-frequency edit-in-place path, per-message so undedupable, not money/state), the `/events` brief feed fetch (`markets::brief` is a pure fn with no `Context` — the user sees "unavailable" and the bet-time fetch already alerts), the stale-button "not in feed" (expected, not an error), and `/dashboard`'s query error (sync `dashboard_text`; the owner runs `/dashboard` and sees the broken result directly).

This matters because `/sell` and `/buy` slash commands **don't transact** — they just post an inline keyboard with a `sell:<seller>:<fruits>:<price>` or `buy:<buyer>:<fruits>:<price>` payload. The actual fruit/coin exchange happens when the counterparty taps the button and the callback fires.

The `envelope:` callback prefix is still routed even though the `/envelope` command was removed: `/send <amount>` replying to a real user is a **direct transfer**; with **no reply target** (or replying to the bot) it posts a red-envelope-style claim button, and that share path uses the same callback.

### `/predict` — host AMM prediction markets

`/predict` (`src/commands/predict.rs`) opens a stateful DM builder wizard (question → options → end-time → a **trading-fee picker** `pmfee:<bps>` 2/5/10% → a **funding-window picker** `pmfund:<minutes>` 1h/6h/24h/3d) that creates an AMM event in its **funding stage** via `Database::create_funding_event(host, …, fee_bps, open_at)` — **no upfront charge** (the seed comes from LPs). `finalize_funding` posts a **placeholder** card first, then renders the funding board and `set_event_card`s it.

**Funding stage (LP price discovery).** While `state = 'funding'` (until `open_at`), anyone provides liquidity. The funding board (`predmarket::funding_text`/`funding_board_rows`) shows each outcome's **implied opening price** (`lmsr_fund::opening_prices` = `fundedₖ / Σ funded`) + coins funded + the pool (with a `✅ ready` / `⚠️ needs ≥ MIN_SEED` note), a `[💧 <name>]` button per outcome, and a host `[✖ Cancel]` (`pm:void:` → `void_event`). Tapping `[💧 name]` opens an owner-locked **amount builder** (`pm:fund:`/`pm:fsz:`/`pm:fgo:`, previewing the opening price the allocation sets) that calls `Database::add_liquidity(event, user, alloc[], now)` — atomically debiting the LP and tallying `markets.funded` (price discovery), their `liquidity` row (pool share), and `events.pool` (the seed). **Uneven allocations are the point**: the pooled funding distribution *is* the opening prices.

**Lazy open.** On the first board interaction after `open_at` (`refresh_card`/`handle_fund` call the now-public `Database::finalize_funding_if_due`), the stage finalizes (in its **own committed tx**, so a void can't be rolled back by the triggering trade): it computes `b = seed / ln(1/p_min)` and the opening baseline `q⁰ = b·ln(p)` from the pooled allocation (`core::lmsr_fund`), writes them to `b_param`/`markets.q_shares`, and flips `funding → open`. If the pool is under-seeded (`< MIN_SEED` coins) it **voids + refunds the LPs** instead. After that it's the ordinary LMSR trading board: each outcome's price + buy buttons + a host `[resolve]`; tapping opens the owner-locked **spend builder** (`pm:sz:`, preview via `amm_buy_quote`) that buys via `amm_buy`.

**Resolution & LP economics.** The host declares the winner (`pm:win:<idx>` → `resolve_event`) or voids (`pm:void:` → `void_event`); **resolving/voiding settles every position immediately** (`handle_win`/`handle_void` → `settle_event`), so winners are paid without any `/claim`. When the last position settles, `settle_event` returns the residual (`pool − winning payouts`, ≥ 0 by the LMSR bound, **plus accrued fees**) to the **LPs pro-rata** by contribution (`lmsr_fund::pro_rata`, exact largest-remainder split). LPs bear **real (bounded) risk**: they earn the fee but bleed subsidy to traders, netting anywhere from ~0 to seed+fees — the skin-in-the-game that makes price discovery real. The single-host path `create_amm_event` (immediate-open, host pays `⌈b·ln k⌉`) still exists for the engine/tests and writes the host as the sole `liquidity` row, so resolution / void / `reset_events` treat one-host and multi-LP events identically. The pure curves are `src/core/lmsr.rs` (trading) + `src/core/lmsr_fund.rs` (funding: `opening_prices`/`seed_to_b`/`opening_q`/`pro_rata`), both conservation-tested. All state lives in the DB — **no in-memory map**.

### Internationalisation (`src/core/i18n.rs`)

Every user-facing string is localized into 18 locales (English + Traditional &
Simplified Chinese + Japanese, Korean, Russian, French, Spanish, German,
Vietnamese, Indonesian, Filipino, Thai, Dutch, Turkish, Português, हिन्दी,
العربية). **Owner-only/admin replies are exempt** — they use plain English
literals in the handler (the owner is one known person), *not* `tr!` functions;
i18n is reserved for genuinely user-facing strings. (Caveat: a string is only
owner-facing if no non-owner ever sees it — e.g. `service_paused`/`im_back` stay
localized because `paused_block` shows them to regular users; the owner's
pause/unpause confirmation just reuses those.) The module is dependency-free: a `Lang` enum, a `tr!` macro that picks
one of 18 literal arms in a fixed order (`en, hant, hans, ja, ko, ru, fr, es, de,
vi, id, fil, th, nl, tr, pt, hi, ar`), and one `pub fn` per message so all locales
for a message sit together. Parameterised messages leave `{token}` placeholders
in every arm and substitute with `.replace(...)` (real `format!` can't take a
runtime format string). The `tr!` match is exhaustive over all 18 variants, so a
new message that omits an arm fails to compile. The picker display order is driven
by `Lang::ALL` (chunked two-per-row in `menu::lang_picker_rows`), *not* the
`tr!`/`native_label` arm order.

Adding a message: add a `pub fn` with all 18 `tr!` arms in the order above; the
`no_unfilled_placeholders_in_any_locale` test catches any arm that drops a token.

Language resolution is **explicit-choice-wins, auto-detect-fallback**. A user's
`/start`-chosen locale is persisted in `balance.lang` (stable `Lang::store_code`,
e.g. `hant`/`hans`, round-tripped via `Lang::from_store_code`; empty = not yet
chosen). When unset, the bot falls back to Telegram's `User.language_code` via
`Lang::from_user`: unknown / unsupported tags → English; bare `zh` → Simplified,
`zh-Hant`/`zh-TW`/`zh-HK`/`zh-MO` → Traditional. Command handlers resolve the
acting user through `commands::util::lang_for(&ctx, &user)` /
`lang_for_msg(&ctx, &msg)` (DB-then-detect); callbacks use the equivalent
`cb_lang`. The detect-only `lang_of(&Message)` remains for sites without DB
access. `Database::{get_lang, set_lang}` are the persistence accessors.

- **Per-user messages** (direct replies, callback toasts) render in the *acting*
  user's locale.
- **Shared/edited messages** (the AMM `/predict` board, the match-bet event card,
  sell/buy listings, the envelope edits) render in the **creator's** locale — the
  `events` row stores a `lang` set from the creator at creation, and the match card
  pins it in the `opt:` callback data so a shared card never flips per tapper.
- **Command menu**: `bot::run` registers a localized `setMyCommands` per locale
  plus a default (English) menu. Telegram only accepts ISO 639-1 codes there, so
  both Chinese scripts collapse to one `zh` menu (`Lang::menu_code`) and Filipino
  best-efforts under `tl`; per-locale failures are logged and skipped.

### `/events` — read-only Polymarket feed (`markets.rs`)

> The slash command is **`/events`** (the fn was renamed from `markets`); the feed module stays `markets.rs` and the internal `menu:markets` callback is unchanged. The browse feed is now distilled into the `SourcedEvent` model (**allowlisted leagues only** — `kind == "sport"` filtered through `ALLOWED_LEAGUES` = `[("FIFA_WC", None), ("LOL", Some("Mid-Season Invitational"))]`, i.e. the World Cup + LoL's MSI, since the feed's `sport` bucket also carries other esports and small regional LoL leagues; a league's optional tournament marker keeps only matches naming it in the English `description`); display/bet odds are the feed's relayed YES prices (the old Gamma odds overlay was removed) — see below.

`src/commands/markets.rs` is the one command that talks to an outside service
rather than the local DB. It `GET`s `https://api.waterx.app/predict/browse`
(via `reqwest` with `rustls-tls`, reusing the rustls already in the tree) and
renders a Jupiter-style "market brief": **allowlisted leagues only** (`kind ==
"sport"` in `ALLOWED_LEAGUES` — World Cup + LoL's Mid-Season Invitational, the
regional LoL leagues filtered out by the per-league tournament marker),
**kicking off within the next 24h or already live** (`within_window`,
applied uniformly to both leagues — team vs team, kickoff time, and per-outcome
**decimal odds** = `100/oddsCents`, e.g. 65¢ → 1.54) — the feed's other esports
`sport` matches (CS2/VALORANT/DOTA2),
`sport-award`, and crypto up/down pools are all filtered out. (An esports match
has no draw side, so it collapses to a 2-outcome `[teamA, teamB]` event vs the
World Cup's 1X2.) The brief shows **`PAGE_SIZE` = 4 matches
per page** with a `[◂ Prev]`/`[Next ▸]` navigation row + a `📄 Page x/y`
indicator (callback `evpage:<m|s>:<page>` → `callbacks::handle_events_page`,
edit-in-place; the `m`/`s` flag = embedded-in-`/start`-menu vs standalone, so the
re-render keeps or drops the menu's back-to-home button). It never touches the
coin ledger. Two gotchas baked into the structs: the response models only
the fields the brief reads (serde ignores the rest), and `oddsCents` **must** be
`f64` — some rounds report fractional cents (e.g. `99.9`), which would make an
`i64` field fail to deserialize the entire feed. The fetch sends `locale=zh` for
Chinese users (Hant/Hans → Chinese team names) and `locale=en` for everyone
else; the brief's chrome is localized separately via `render(lang, …)`. (Note:
only the `?locale=` query form works — a `/en/predict/browse` path 404s.)
`fetch_markets` is served from a process-wide **5-second per-locale cache**
(`FEED_CACHE_TTL` = 5s, `feed_cache()` = `OnceLock<Mutex<FeedCache>>`, keyed by
the `en`/`zh` API locale) so repeated `/markets`, `menu:markets`, and `bet:` taps
don't hammer the rate-limited API — the lock is never held across the network
`.await`. Every real-money placement **re-prices from this cache at place time**
(`betting::refetch_quote`, see the betting section), so a wager is always booked
from a feed snapshot **at most `FEED_CACHE_TTL` (5s) old** — never the older
snapshot the quote was locked to. The
displayed quote keeps its own 10s `QUOTE_TTL_SECS` purely for the build/confirm
UI (auto-renewed past that). Concurrent cold-cache misses
aren't coalesced, so a startup burst may fetch a couple of times before the cache
warms.

**Odds: waterx relay, no Gamma overlay.** Display *and* bet odds are the waterx
feed's `oddsCents` — itself Polymarket's relayed YES price — so there is **no
separate per-event Gamma odds fetch** (an earlier overlay was removed: a
multi-outcome event would mean one Gamma call per candidate, and waterx already
relays the price). `markets::group_events` distils the feed into
`SourcedEvent { key, title, outcomes: [{ name, yes_cents }], starts_at, ends_at,
live }` — an outcome-list model (the bet/sell flow is **outcome-index based**), but
**allowlisted leagues only**: `group_events` keeps only `kind == "sport"` matches
whose `display.league` is in `ALLOWED_LEAGUES` = `[("FIFA_WC", None), ("LOL",
Some("Mid-Season Invitational"))]` (World Cup + LoL/MSI — add a `(league,
tournament?)` row to surface a league; a `Some(marker)` keeps only matches whose
English `description` names that tournament, so LoL's small regional leagues like
Prime League are dropped), with outcomes in the fixed `[teamA, draw, teamB]` order
(matching `gamma_resolution`'s idx convention; an esports match with no `draw`
side collapses to `[teamA, teamB]`). The `sport` bucket also carries other
**esports** (CS2/VALORANT/DOTA2, slug `sport-<game>-…`) — those are dropped along
with `sport-award` (awards + props) and `crypto`, none of which are ingested — the
other feed categories were investigated and dropped: awards are multi-outcome (not
wanted), crypto is up/down noise, and **props can't auto-resolve** — waterx exposes
no identifier that maps to a prop's Gamma market (its slug is reworded+timestamped
and its `trade.marketId` ≠ the Gamma `conditionId`), so a prop would need manual
owner resolution. (Sport works only because its `sport-<ticker>` slug maps 1:1 to
the Gamma event slug.) Gamma
(`gamma-api.polymarket.com/events/slug/<ticker>`, `GAMMA_EVENT_URL`) is now hit
**only by `gamma_resolution`** to detect a settled match (`outcomes`/`outcomePrices`
arrive as JSON-encoded strings, parsed lazily by `GammaMarket::yes_cents` — YES
price × 100 = the bot's cents convention). The crate `polymarket_client_sdk_v2` was
evaluated and **deliberately not used** — its read path pulls in a non-optional
`alloy` (signers + sol-types) and wants `reqwest 0.13` (vs the tree's `0.12`), so we
hit Gamma directly with the existing `reqwest`.

`/events` renders the brief with a **numbered button per shown event**
(`bet:<key>`, the event key = a sport slug); `markets::brief` returns `(text, button
rows)` and `fetch_one(key)` re-fetches a single event's fresh odds at bet time.
`SourcedEvent`/`SourcedOutcome` are the distilled structs shared by both;
`render_market` renders any number of outcomes (`name — odds`, caller's format).

### Match betting — buy/sell shares on `/events`

`src/commands/betting.rs` drives the **buy** flow for `sourced` (Polymarket) events on the share model: tap an event (`bet:<key>`) → its card (one odds button per outcome, `opt:<lang>:<fmt>:<key>:<idx>` — the outcome **index**) → pick an outcome → a **spend builder** (`sz:`/`szp:`, presets accumulate) → **Confirm** (`szp:`). **Back navigation is private-only** (`option_rows`/`builder_text_rows` take an `is_group` flag): in a DM the card carries a `[⬅ Back]` → `menu:markets` (back to the brief) and the spend builder a `[⬅ Back]` → `bet:<key>` (back to the card), so the flow never dead-ends. In a **group** these are omitted — the card is a shared surface (a back tap would yank everyone out of it) and the builder is a per-user reply board with its own `[Dismiss]` (`bx:`). re-prices from the ≤30s feed cache (`refetch_quote`) and **buys YES shares at the current price** via `get_or_create_sourced_event` + `Database::sourced_buy` (house-banked: `shares = ⌊spend/price⌋`, the spend leaves circulation; `source_ref` = the event key, outcomes in the feed's order — sport `[teamA, draw, teamB]` — bought by the tapped index). The `Quote` carries `{key, title, outcomes: Vec<SourcedOutcome>}` and is keyed entirely by outcome index (no `teamA/draw/teamB` strings). A YES share settles to 1 coin, so the "potential payout" shown is the share count — the same numbers the old fixed-odds flow displayed, but the position is now **sellable** before settlement. **Repeated buys of the same (event, outcome) merge into one position** — `Database::add_position` upserts on the `positions` PK `(event_id, market_idx, user)`, summing `shares` + `cost` (and sourced events are reused by `source_ref`), so the cost basis accumulates in a single row. The **sell** flow (`src/commands/selling.rs`): `[💸 Sell]` on the private Check-assets view → a **picker of holdings rendered as a numbered brief** (`selling::sell_picker`, mirroring the `/events` feed: each holding is a text line `<n>) <event title>\n  <outcome> · 🪙<cost> → 🏆<shares>` with a numbered button `[1] [2] …` 4/row → `slb:<event>:<idx>:0`) — the **event title is shown** so a bare outcome like "Draw" is identifiable by its match (the old one-button-per-row label was just `<outcome> · <shares>`, ambiguous across events) → a share-amount builder (`slb:`, live proceeds via `sell_context` + `amm_sell_quote` for amm / `fetch_one` + the held outcome's index for sourced; the builder + the sell confirmation both **lead with the event title** `SellContext.title` for the same reason) → `sourced_sell`/`amm_sell` at the live price. The builder's quick-pick buttons are **fractions of the holding** — `[25%] [50%] [75%] [Max]` (`SELL_FRACTIONS`), each **setting** the amount to that share of `held` (not additive), the target micro-shares riding in the `slb:` callback data. **Terminal private nodes carry a `[🏠 Home page]` row** (`menu::home_row(lang)` → `menu:home`) so an edit-in-place flow never dead-ends — the buy placed/expired confirmations (`betting`), the AMM buy/fund confirmations (`predmarket`), and the `/predict` builder's "created"/"failed" DM. (Group paths instead delete the board + post a shared announce, so they get no home button.) A sell reports the **cost basis removed** (`TradeOutcome::Filled.basis` — the whole basis on a full sell, else floored pro-rata via `basis_for_sold`), so the confirmation shows **realized P&L = `coins − basis`** with a 📈/📉/➖ direction marker (`selling::pnl_line` → `i18n::sell_pnl`, signed via `util::fmt_signed_coins`). The **sell builder previews the same P&L live** as you change the amount: `SellContext.basis` (the held position's total cost) lets `build_screen` show `proceeds − basis_for_sold(basis, micro, held)` — the same helper the sell executes with, so the estimate matches the result (modulo a sourced re-price at confirm).

**Settlement is automatic — there is no `/claim`.** A **5-min background task** (`bot::run` spawns it; body = `settle::auto_settle` → `settle::sweep`) detects Polymarket (Gamma) resolution for every open `sourced` event, caches the winner on the row (`resolve_event`), then pays out **every** resolved/void position via `Database::settle_all_resolved` → `settle_event` (winning shares pay 1 coin each, losers 0, a void refunds cost basis). **Each credited user is then DM'd** (`settle::notify_settled`): winners get `i18n::bet_won`, void-refundees `i18n::bet_refunded`, in the user's saved locale (English fallback) — every payout with `coins > 0`; pure losers (`coins == 0`) get nothing. It's **best-effort per user** (a DM to someone who bet in a group but never started the bot just fails and is skipped — the coins already landed on their balance) via the token-based `tg::send_text_token` (a raw Bot-API `sendMessage`, because the task runs outside the telexide framework and so has no `Context` — the token is passed into the spawned task from `bot::run`). Whichever path settles an event first (the task or the manual `/settle`) sees its payouts and sends the DMs; the other gets an empty list, so a user is never double-notified. **AMM `/predict` events settle instantly** when the host resolves/voids (`predmarket::handle_win`/`handle_void` call `settle_event` right after `resolve_event`/`void_event` — winners paid + LP residual returned immediately), with the sweep as the backstop. `/settle` (public) is the manual fallback running the exact same `sweep`. The **auto-detect** step is `markets::gamma_resolution(slug, n_outcomes)` — the Gamma event is `closed`; the pure, unit-tested `GammaEvent::winning_idx(n)` reads the winner from Gamma's English data and maps it **positionally** into the event's stored `[teamA, draw?, teamB]` order: teamA (named first in the title) → `0`, the draw → `1`, teamB → the last outcome `n−1`. That one rule covers both the 3-way World Cup shape — per-team `Yes/No` markets, the winner's YES ≈ 1 — and the 2-outcome LoL shape — a single multi-outcome `"Match Winner"` market with team-name outcomes, the winner priced ≈ 1; Yes/No **prop** markets are skipped by requiring the YES market's title to be a team named in the event title. The outcome count comes from `all_open_sourced`, which returns `(id, slug, outcome_count)`.) and caches the winner on the event row (`resolve_event`), so a later sweep reuses it. `amm` events are host-resolved and settle instantly (see `/predict`). AMM settlement pays winners from the `pool` and returns the residual to the host once the last position is settled (the event → `closed`); sourced settlement is house-banked (mints the winning payouts).

Both the buy spend-builder and the AMM stake-builder post the tapper their **own owner-locked board** as a reply to the shared event card (a new in-group message, or edit-in-place in a private chat), so the card stays tappable by everyone; the running total rides in the callback data (no server-side per-user state), and every placement re-prices from the ≤30s feed cache so a trade always books at the current price. **`/settle`** (`src/commands/settle.rs`, **public** — settlement is deterministic) is the **manual fallback** for the 5-min auto-settle task: it runs the same `settle::sweep` — auto-detect Gamma resolution for every open `sourced` event, then `Database::settle_all_resolved`, which settles **both** sourced *and* any host-resolved AMM event (in case an AMM resolve-time settle ever failed) — and DMs each winner/refundee via the shared `settle::notify_settled` (same as the auto task) before replying to the caller with the sweep summary. `sweep`/`settle_all_resolved` now return a `database::SettleReport { payouts, failed }`; a non-empty `failed` (an event whose settle tx errored — money that didn't move) **alerts the owner** (both the command and the auto task), and the next sweep retries it.

**Owner manual resolution — the Polymarket-down escape hatch.** When Gamma is unreachable (or returns a result the mapper can't read), `gamma_resolution` errors and nothing auto-resolves, so a settled match could sit `open` forever. To break that, when the **owner** runs `/settle` it additionally posts a **manual picker** (plain-English, owner-only, callback prefix `mstl:`): the sweep summary + one button per **finished** still-open `sourced` event (`Database::open_sourced_events(now)` → `mstl:pick:<id>`). "Finished" = `ends_at > 0 AND ends_at < now` (the match's feed end time is known and past), so a match **still in progress is never offered** for manual settlement — only genuinely-ended events the sweep couldn't resolve. (Edge: a sourced event with an unknown end time `ends_at == 0` — anomalous, the feed normally provides it — is never listed.) Tapping an event opens its **outcome picker** (`Database::sourced_outcomes` → the event title + its `markets` outcomes as `[<name>]` buttons `mstl:win:<id>:<idx>`, a `[🚫 Void (refund all)]` `mstl:void:<id>`, and a `[⬅ Back]` `mstl:list`). Picking a winner runs `resolve_event(id, idx) → settle_event(id, None)` (void runs `void_event → settle_event`), pays + DMs everyone via `notify_settled`, and re-renders the (now shorter) list in place; every handler is **owner-gated** (`util::is_owner`, silent ack otherwise) since the picker may be posted in a group. Non-owners running `/settle` get only the localized auto-sweep summary as before. The handlers live in `settle.rs` (`handle_manual_pick`/`handle_manual_win`/`handle_manual_void`/`handle_manual_list`), routed in `callbacks::on_callback`.

### Database

`src/database/` wraps a single `rusqlite::Connection` in a `parking_lot::Mutex` so `Database` is `Send + Sync` behind an `Arc`. Split by concern: `mod.rs` (struct + schema + migrations + `COIN` + `reset_all` + `ensure_row` + balance backup/restore), `user.rs` (balance/`UserRow` in micro-coins, check-in + referral cascade), **`event.rs`** — the **unified market engine**: owns the `events`/`markets`/`positions`/`liquidity` schema + the `SHARE`/`B_MEDIUM`/`FEE_BPS_*`/`MIN_SEED` consts, and the whole trade/settlement API (`create_amm_event`/`create_funding_event`/`add_liquidity`/`finalize_funding_if_due`, `sourced_buy`/`sourced_sell`, `amm_buy`/`amm_sell` + the read-only `amm_buy_quote`/`amm_sell_quote`, `resolve_event`/`void_event`, `settle_event`/`settle_all_resolved`/`reset_events`, plus the `user_positions`/`sell_context`/`amm_board`/`all_open_sourced`/`event_card` accessors) — funding-stage curve math (opening prices, `b` from the pooled seed, LP pro-rata) lives in `src/core/lmsr_fund.rs`; see the money-model invariant. Then `fruit.rs`, `buffer.rs`, `meta.rs` (pause flag), `chats.rs` (seen chats + group adder), `referral.rs`, `dashboard.rs`, `history.rs` (the append-only `/history` action log — the `HK_*` kind tags, the in-transaction `record` helper the money paths call, the standalone `record_action` for `/mint`, and the `user_history` read). The only legacy survivor is `wager.rs` = `decimal_payout` (the buy builder's payout preview). The old fixed-odds `wagers` system, the pari-mutuel `games`/`Prediction` system (`predictions.rs`, `core/prediction.rs`), their tables, and the one-time `/migrate`/`schema_version` cutover are all **gone** — `Database::new` drops the stale tables on boot. All sub-files add methods to the same `impl Database` block. Balances/shares are `i64` micro-units.

## Non-obvious gotchas

- **`InlineKeyboardButton::new(text, pay)`** takes two args. The second is `pay: bool` (a Telegram payment-button flag) — telexide's `#[build_struct]` macro promoted it to mandatory because it isn't `Option<T>`. Pass `false` unless you're actually building a payment button.
- **`rand::thread_rng()`** returns a non-`Send` `ThreadRng` — scope it in a block that ends before any `.await`, or the `#[command]` future fails the `Send` bound.
- **The `_COMMAND` statics are pub-glob-reexported** (`pub use start::*`) so `create_framework!(name, start, assets, ...)` can resolve them at the bot.rs call site. Don't move command fns into private modules or the macro expansion will fail to resolve `<name>_COMMAND`.

## Configuration

Env vars consumed by `BotConfig::from_env` (see `src/core/types.rs`): `BOT_TOKEN` / `BOT_OWNER` (required) and optional `BOT_DEV` (default `true`). `BOT_DEV` also selects the SQLite data file via `database::db_filename` — `waterx-dev.db` (dev, default) vs `waterx.db` (production). Both match the `*.db` gitignore rule. `bot.rs::run` calls `BotConfig::from_env`. `main` picks the dotenv file via the `ENV_FILE` var: unset → default `.env` lookup (production); set → that file (`ENV_FILE=.env.dev cargo run` for the dev bot). The repo ships two gitignored configs — `.env` (production, `BOT_DEV=false`) and `.env.dev` (development, `BOT_DEV=true`) — with `.env.example` / `.env.dev.example` as their tracked templates. Dev and production **must** use different bot tokens: one Telegram token can't be polled by two running bots at once (getUpdates conflicts).
