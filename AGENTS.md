# AGENTS.md

Guidance for coding agents working in this repository. Both Claude Code (v2.1.281+) and Codex read this file. Do not add a CLAUDE.md anywhere in the repo: Claude Code ignores every AGENTS.md at or below a directory that has one. `src/` is the reference for how each command, callback and table behaves; this file holds what the source cannot tell you. `docs/design.md` narrates each feature flow for humans; it is not loaded and not kept in step with `src/`, so where the two disagree the code wins.

## What this is

A Telegram bot for a small private group, written in Rust on top of [`telexide`](https://docs.rs/telexide). The headline feature is a Polymarket-style prediction market: browse live events and buy YES shares of an outcome at the current price, then sell them back before settlement. Two event kinds share one engine — `sourced` (Polymarket-backed, priced live from the waterx feed, house-banked) and `amm` (host-run via `/predict`, priced by an LMSR market maker, LP-funded through a funding stage that discovers the opening prices). Around that sit a coin ledger + transfers, fruit trading, and a daily check-in. State persists in a SQLite file chosen by the `BOT_DEV` flag via `database::db_filename(dev)`: `waterx-dev.db` for development (the default) and `waterx.db` for production (`BOT_DEV=false`), so a dev bot never clobbers live balances.

**Coin-supply invariant.** The house mints coins (grows supply) only via (a) the daily check-in, (b) referral rewards, and (c) a player winning a `sourced` market. Host-run `amm` predictions never mint — they are a closed redistribution between the LPs (who seed the funding pool, bearing real bounded risk for the trading fee) and the traders, with the residual returned to LPs pro-rata. The engine's directed rounding is always pool-favourable, so an AMM escrow cannot be drained below the winners' obligations. The trade engine is `src/database/event.rs` (+ the pure curves in `src/core/lmsr.rs` and `src/core/lmsr_fund.rs`), conservation-tested.

## Architecture

**Framework version.** `Cargo.toml` pins `telexide = "0.1.17"`, the latest published release; `Cargo.lock` is committed and CI builds `--locked`. Check `https://crates.io/crates/telexide` before bumping.

**One file per command.** `src/commands/<name>.rs` holds exactly one `#[command]`-annotated async fn. `commands/mod.rs` re-exports each with `pub use <name>::*;` so the proc-macro-generated `<name>_COMMAND` static is also re-exported. `src/bot.rs` does `use crate::commands::*;` and lists every command identifier in `create_framework!` — adding a command means a new file under `src/commands/`, `pub mod foo;` + `pub use foo::*;` in `src/commands/mod.rs`, and `foo` appended to the `create_framework!` ident list in `bot.rs`.

**Shared state via `TypeMapKey`.** `bot.rs` defines `DbKey`, `ConfigKey`, `BotIdKey`, `BotUsernameKey`, `QuotesKey` (the match-bet quote store) and `ConvosKey` (in-flight `/predict`/`/feedback` DM drafts). Handlers reach DB state through `db(&ctx) -> Arc<Database>` in `src/commands/util.rs`. These helpers encapsulate the Send-across-await gotcha: `ctx.data.read()` returns a `parking_lot::RwLockReadGuard` that is not `Send`, so it cannot be held across `.await`. The helpers grab the value and let the guard drop on the same statement — go through them rather than calling `ctx.data.read()` inline.

**Callback queries are routed separately.** Inline-button presses are not commands. They come through `src/commands/callbacks.rs::on_callback`, a `#[prepare_listener]` registered via `add_handler_func` in `bot.rs`, which matches `UpdateContent::CallbackQuery` and dispatches on the `cb.data` string prefix (the prefix → handler map is in `callbacks.rs` itself; `docs/design.md` narrates each flow). Two more listeners there: `on_my_chat_member` records who added the bot to a group (`chats.added_by`) and `on_new_members` records who added each member (`group_adds`), both feeding the group-add referral. `/sell` and `/buy` slash commands do not transact — they post a keyboard, and the fruit/coin exchange happens when the counterparty taps. The `envelope:` prefix has no command of its own: `/send <amount>` with no reply target posts a red-envelope claim button that routes there.

**All inline keyboards go through `src/commands/tg.rs`.** telexide 0.1.17 serialises `InlineKeyboardButton` with `"url":null` and Telegram rejects it, so markup is built as raw `serde_json::Value` and posted via `API::post` (the header of `tg.rs` explains). Photo uploads likewise go through `tg::send_photo_bytes` (direct multipart via `reqwest`): telexide's own upload names the multipart part wrongly and the upload silently fails.

**Logging** is error-only on stderr via `eprintln!`, with one exception: a single startup line printed by `bot::run` right before the poll loop. Keep new logging to error paths. Failures the operator should act on but would not otherwise see also DM the `BOT_OWNER` via `util::alert_owner` (handlers) / `util::alert_owner_token` (background tasks with no `Context`), which share a 5-min dedup throttle (`ALERT_DEDUP_WINDOW`) so a persistent failure cannot flood the owner or trip Telegram's rate limit — the log is never throttled, only the DM. Wire new money/state-integrity failures into it; leave poll-loop/startup errors, the feedback owner-DM failure (circular) and high-frequency edit failures as `eprintln!` only.

## Money model and atomicity

Balances are integer micro-coins (`database::COIN = 1_000_000` units = 1 coin), kept as `i64` — not `u64`: SQLite integers are signed, ledger deltas are signed, and the non-negative invariant is enforced by `balance_change`'s guard, not the type. Outcome shares use the same unit (`event::SHARE = 1_000_000`) and `SHARE == COIN`, so a winning share settles to exactly one coin. LMSR/price math runs in `f64` then quantizes at the ledger boundary with pool-favourable directed rounding (buy shares floored, sell refunds floored). User-typed whole-coin amounts are multiplied by `COIN` at the ledger boundary and converted with `util::to_micro` (caps at `MAX_COINS`, `checked_mul`) so a crafted stake cannot overflow `i64`; `util::fmt_coins` rounds to at most 2 decimals for display only. Balances are stored directly in micro-coins with no startup rescale. There is no debt path.

**Atomicity invariant.** `balance_change` is a single conditional `UPDATE … WHERE balance + ?1 >= 0` (atomic, no read-then-write TOCTOU), and every multi-statement money/state mutation runs inside one rusqlite transaction — transfers, the share-trade engine (`sourced_buy`/`sourced_sell`, `amm_buy`/`amm_sell`, `create_*_event`/`add_liquidity`, `settle_event`/`settle_all_resolved`), referral legs, `try_checkin` (reward + upline cascade), `claim_envelope` (delete-then-credit, exactly-once under concurrent taps), the startup `refund_and_prune_old_buffer`, and the `buffer` escrow/fill/refund paths. A mid-sequence failure can never leave money half-moved, and concurrent debits cannot overdraw. The append-only `history` table is written inside the same transaction as each money move (`history::record` just before `tx.commit()`), so the statement cannot drift from the ledger. Two places differ: the owner `/mint` logs best-effort via `Database::record_action`, and a red envelope's `send_out` rides in `insert_buffer`'s tx rather than the earlier debit's, because the Telegram post sits between the two. DB read failures fail safe: `assets`/`/settle`/`/broadcast` surface the error instead of a fake zero, and the pause kill-switch fails closed (an unreadable `is_paused` blocks non-owners; the owner is checked first so they can still `/unpause`).

**`/predict` economics.** An AMM event starts in a funding stage with no upfront charge: LPs allocate coins per outcome (`Database::add_liquidity`), and the pooled allocation *is* the opening prices (`lmsr_fund::opening_prices`). On the first board interaction after `open_at`, `finalize_funding_if_due` runs in its own committed tx (so a void cannot be rolled back by the triggering trade), computes `b` and the opening baseline, and flips `funding → open` — or voids and refunds the LPs when the pool is under `MIN_SEED`. Resolving/voiding settles every position immediately; the residual (`pool − winning payouts`, ≥ 0 by the LMSR bound, plus accrued fees) goes to LPs pro-rata (`lmsr_fund::pro_rata`, exact largest-remainder split). All state lives in the DB — no in-memory map.

**Settlement is automatic — there is no `/claim`.** A 5-min background task (`settle::auto_settle` → `settle::sweep`) detects Gamma resolution for open `sourced` events and pays every resolved/void position via `settle_all_resolved`; `/settle` (public) is the manual fallback running the same sweep, and the owner additionally gets a manual picker (`mstl:`) for finished events Gamma could not resolve. `sweep` returns a `SettleReport { payouts, failed }`; a non-empty `failed` is money that did not move and alerts the owner; the next sweep retries it. Settling deletes the positions, so whichever path settles an event first gets its payouts (and sends the winner DMs) and the other gets an empty list — nobody is notified twice.

## Internationalisation (`src/core/i18n.rs`)

Every user-facing string is localized into 18 locales; owner-only/admin replies are exempt and use plain English literals (the owner is one known person) — but a string is only owner-facing if no non-owner ever sees it (`service_paused`/`im_back` stay localized because `paused_block` shows them to regular users). The module is dependency-free: a `Lang` enum, a `tr!` macro that picks one of 18 literal arms in a fixed order (`en, hant, hans, ja, ko, ru, fr, es, de, vi, id, fil, th, nl, tr, pt, hi, ar`), and one `pub fn` per message so all locales for a message sit together. Parameterised messages leave `{token}` placeholders in every arm and substitute with `.replace(...)`. The `tr!` match is exhaustive, so a new message that omits an arm fails to compile; the `no_unfilled_placeholders_in_any_locale` test catches an arm that drops a token. The picker order is `Lang::ALL`, not the arm order.

Language resolution is explicit-choice-wins, auto-detect-fallback: `balance.lang` (`Lang::store_code`) when set, else Telegram's `User.language_code` via `Lang::from_user` (bare `zh` → Simplified; `zh-Hant`/`zh-TW`/`zh-HK`/`zh-MO` → Traditional; unknown → English). Handlers resolve the acting user through `util::lang_for` / `lang_for_msg`; callbacks use `cb_lang`. Per-user messages render in the acting user's locale; shared/edited messages (the AMM board, the match card, listings, envelope edits) render in the creator's locale — the `events` row stores it, and the match card pins it in the `opt:` callback data so a shared card never flips per tapper. Telegram's `setMyCommands` only accepts ISO 639-1 codes, so both Chinese scripts collapse to one `zh` menu and Filipino best-efforts under `tl`.

## `/events` feed (`src/commands/markets.rs`)

The one command that talks to an outside service: it `GET`s `https://api.waterx.app/predict/browse` (reqwest + rustls) per owner-configured `LeagueFilter` (`/leagues`, persisted in `meta.allowed_leagues`) and renders a paged brief. Gotchas baked into the structs: the response models only the fields the brief reads, and `oddsCents` must be `f64` — some rounds report fractional cents (e.g. `99.9`), which would make an `i64` field fail to deserialize the entire feed. Only the `?locale=` query form works (a `/en/predict/browse` path 404s). The endpoint's real filter params are `type` (an enum; `category=` is silently ignored) and `league` (lowercase); LoL is `type=esports&league=lol`, not `type=sport`.

`fetch_markets` is served from a process-wide per-locale cache with `FEED_CACHE_TTL` = 5 s (the lock is never held across the network `.await`). Every real-money placement re-prices from this cache at place time (`betting::refetch_quote`), so a wager is always booked from a snapshot at most 5 s old, never the snapshot the quote was locked to; the displayed quote keeps its own 10 s `QUOTE_TTL_SECS` purely for the build/confirm UI. Gamma (`GAMMA_EVENT_URL`) is hit only by `gamma_resolution` to detect a settled match; the winner is mapped positionally into the stored `[teamA, draw?, teamB]` order. The crate `polymarket_client_sdk_v2` is deliberately not used — its read path pulls in a non-optional `alloy` and wants `reqwest 0.13` against the tree's `0.12` — so Gamma is hit directly with the existing `reqwest`.

## Database

`src/database/` wraps a single `rusqlite::Connection` in a `parking_lot::Mutex` so `Database` is `Send + Sync` behind an `Arc`. Split by concern — `mod.rs` (struct + schema + migrations + `COIN` + `reset_all` + backup/restore), `user.rs` (balance, check-in + referral cascade), `event.rs` (the unified market engine: `events`/`markets`/`positions`/`liquidity` and the whole trade/settlement API), `fruit.rs`, `buffer.rs`, `meta.rs`, `chats.rs`, `referral.rs`, `dashboard.rs`, `history.rs` — and all sub-files add methods to the same `impl Database` block. `wager.rs` only keeps `decimal_payout`. `Database::new` best-effort `DROP TABLE IF EXISTS`es the pre-rewrite `wagers`/`games`/`game_options`/`game_stakes` tables on boot and drops the vestigial `balance.cloth` column. Backups are a rolling whole-DB file snapshot (`VACUUM INTO` + atomic rename, every `BACKUP_INTERVAL` in production, first one an interval after boot so a crash-looping deploy cannot clobber the last good copy); restore is a file swap with the bot stopped.

## Non-obvious gotchas

- **Owner commands** (`mint`, `pause`, `reset`, `dashboard`, …) are gated on `util::is_owner`, ignore non-owners silently, and stay out of the `/` menu. The `[Everything]` `/reset` writes a DB snapshot first and aborts the wipe if it cannot.
- **Group chats see one shared message**, so nothing private renders there: `/assets` hides the balance in a group (`util::is_group_chat`) and `/balance` is the explicit opt-in. With Telegram privacy mode the bot only receives commands, button callbacks and service messages in groups — plain chatter never reaches it.
- **Edit-in-place flows never dead-end**: terminal private screens carry a `menu::home_row` button back to `menu:home`.

- **`rand::thread_rng()`** returns a non-`Send` `ThreadRng` — scope it in a block that ends before any `.await`, or the `#[command]` future fails the `Send` bound.
- **The `_COMMAND` statics are pub-glob-reexported** (`pub use start::*`) so `create_framework!(name, start, assets, ...)` can resolve them at the `bot.rs` call site. Don't move command fns into private modules or the macro expansion will fail to resolve `<name>_COMMAND`.
- **The daily check-in is on a fixed 00:00 UTC boundary**, never local midnight, so a user cannot farm it by hopping timezones; all other absolute times render in the caller's `tz_offset` in private chats and UTC in groups.
- **Referral binding is a one-way `referrer` `0 → set` transition** (`set_referrer_if_unset`, `bind_group_referral`), so each referee pays out at most once; both bind sites run before the command creates the user's row.

## Configuration

Env vars consumed by `BotConfig::from_env` (`src/core/types.rs`): `BOT_TOKEN` / `BOT_OWNER` (required) and optional `BOT_DEV` (default `true`). `BOT_DEV` selects the SQLite data file via `database::db_filename` — `waterx-dev.db` vs `waterx.db` — and gates `/reset` and `/delete` (`util::is_dev`, so they can never fire on a production bot). `DATA_DIR` names the directory for the DB and its `.bak` snapshot; on Railway it must be a mounted volume or every balance is lost on the next deploy. `main` picks the dotenv file via `ENV_FILE`: unset → `.env` (production); `ENV_FILE=.env.dev cargo run` for the dev bot. `.env.example` / `.env.dev.example` are the tracked templates. Dev and production must use different bot tokens: one Telegram token cannot be polled by two running bots at once (getUpdates 409), which is also why `railway.toml` pins `numReplicas = 1`. Deploys are git-push driven on Railway (`main` → production, `dev` → test bot); there is no in-bot redeploy command.
